# P4-10 Monitoring Foundation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a bounded, privacy-preserving monitoring foundation for the single-process API: keep liveness backwards compatible, expose metadata readiness, and provide owner-protected HTTP request counters.

**Architecture:** The HTTP server owns one thread-safe in-process `MetricsRegistry` with bounded canonical route labels. The application exposes a redacted readiness snapshot that checks only the configured metadata backend through its existing storage port. `/api/v1/health` remains unauthenticated liveness; `/api/v1/ready` is unauthenticated but reports `503` when metadata is unavailable; `/api/v1/metrics` requires the existing `owner:read` scope and emits deterministic Prometheus text without owner IDs, paths, tokens, or provider data.

**Tech Stack:** Python 3, `unittest`, `http.server`, existing `MetadataStore` protocol, existing owner-scope authentication, Prometheus text exposition format.

---

## Scope and exclusions

- Include: metadata readiness probe, request totals by method/route/status, in-flight request gauge, bounded label cardinality, deterministic metrics response, focused unit/integration tests, README/privacy documentation.
- Exclude: external Prometheus push or scrape configuration, alerting, tracing, log shipping, SLOs, provider health checks, blob-store health checks, distributed aggregation, and persistent metric storage. Metrics reset on process restart.
- Preserve the existing `/api/v1/health` response shape and public access behavior.
